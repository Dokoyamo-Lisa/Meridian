# Architecture

```
 browser / API / MCP                         servers (one agent each)
 status page, users' pages                   ┌──────────────────────────────────────┐
        │  HTTPS                             │ meridian-agent (root; systemd/OpenRC) │
        ▼                                    │   ├─ Xray        (meridian-xray)      │
 ┌───────────────┐   long-poll state  ◄──────┤   ├─ Hysteria2   (meridian-hy2@N)     │
 │ meridian      │   signed + sealed         │   ├─ WireGuard   (kernel, wgctrl)     │
 │  panel        │                           │   ├─ nftables    (table inet meridian)│
 │  SQLite (WAL) │   reports (traffic, IPs,  │   ├─ realm       (meridian-realm@N)   │
 │  web UI       │ ◄─ destinations, health) ─┤   └─ ACME        (Let's Encrypt, :80) │
 └───────────────┘                           └──────────────────────────────────────┘
```

## People

- **The supervisor** is the one account that signs in to the panel (with optional two-factor
  sign-in). API tokens act for it, read-only or with full access.
- **Users** are the people who connect. Each has a subscription link and, optionally, a username
  and password for their own page (`/me`). User sessions use their own cookie and table; none of
  the panel's API accepts them, and the user API (`/api/portal/*`) accepts nothing else.

## Desired state

The panel compiles, for every server, a complete **desired state**: the Xray inbounds and their
users, Hysteria2 nodes and users, WireGuard interfaces and peers, port forwards, blocked IPs, the
country rule, certificates to obtain, core versions and pending actions. Its content hash is the
**revision**.

The agent long-polls `GET /agent/v1/state?rev=<current>&wait=50`. The panel answers as soon as the
revision differs, or with `204` after the wait. Any change in the panel (a new user, a pause, a
protocol edit, a country rule) recompiles the affected servers and wakes their polls, so changes
reach servers in well under a second. The agent stores the last state on disk and re-applies it on
restart, so a server keeps serving even while the panel is unreachable.

## Protocols

A protocol (a "node") is a kind - VLESS, VMess, Trojan, Shadowsocks, SOCKS5, HTTP, Hysteria2 or
WireGuard - plus its settings: transport (raw, WebSocket, gRPC, HTTPUpgrade, XHTTP), security
(REALITY, TLS, none) and the kind's own options. One function decides whether a combination is
valid; the same code renders the server configuration and every subscription format, and the list
of apps that support a protocol is computed by asking each format's renderer whether it can express
it. So a combination the panel accepts always works on the server and in the apps it lists.

Credentials are derived per user and protocol from the user's secret (HMAC), so adding a protocol
needs no new per-user data, and **Reset credentials** changes them all at once. Imported protocols
keep the IDs and passwords their users already had (stored as overrides), so imported devices keep
working.

Certificates are self-signed (generated by the panel and pinned in client configs that can pin -
formats that cannot pin leave the protocol out; certificate checks are never turned off), pasted by
the supervisor, or obtained by the agent from Let's Encrypt over HTTP-01 on port 80 and
renewed by it; Xray reloads certificate files without a restart. REALITY can front the server's own
website (`127.0.0.1:<port>`) instead of a public site.

## Applying without restarts

The agent diffs the desired state against what runs and changes only the difference, through each
core's live interface:

| Core | How changes apply |
| --- | --- |
| Xray | users are added and removed with the gRPC `HandlerService` (`AlterInbound`); inbounds, outbounds and routing rules are replaced with `xray api adi/ado/adrules` after `xray run -test` validates the full configuration. |
| Hysteria2 | users authenticate against the agent over HTTP, so user changes only update an in-memory table; online users that lose access are kicked through the traffic-stats API. A node's server restarts only when its own port, certificate or obfuscation changes. |
| WireGuard | peers are added and removed on the running interface (wgctrl). |
| nftables | the whole `inet meridian` table is replaced in one atomic transaction; conntrack keeps existing NAT mappings. |
| realm | one service instance per forward: editing a forward restarts only that forward. |

Changes that genuinely need a restart (a different Xray core version, for example) are **not**
applied on their own: the server reports them as "pending restart", the panel shows a warning, and
the supervisor clicks **Restart now**. Nothing pauses on its own either: quotas, expiry dates and
IP limits raise alerts and wait for a person.

Cores run as their own services - systemd units, or OpenRC services on Alpine Linux - so restarting
or upgrading the agent never interrupts traffic. `internal/agent/service` describes each service once
and writes it for whichever init system the server runs.

Servers whose provider decides their ports (NAT servers, LXC and Incus containers) carry the
provider's forwarding as `public_ports` (`internal/panel/ports.go`): new protocols and forwards get
one of those ports, others are refused, links and proxy passes use the public number, and Let's
Encrypt's check is answered where the provider forwards port 80. The agent only ever sees the ports
on the server itself.

On a server without nftables (a bare Alpine, for example) the agent runs everything else and skips
the firewall: WireGuard, kernel port forwards, country rules, IP blocks and the loopback guard need
it. The agent reports what the host supports; the panel refuses what cannot work there (with the
command that fixes it), makes realm the default forward engine, and the server page lists what does
not apply. Installing nftables later is noticed within seconds.

## Country rules

The panel turns country codes into merged address ranges from the DB-IP country database (downloaded
monthly). The state carries only the rule and the list's SHA-256; the agent fetches the list itself
(`/agent/v1/geo/<hash>`, signed and sealed like the state) and keeps a copy for restarts. It is
loaded into nftables sets and checked in both directions - so packets of connections that were
already open from a newly blocked country are dropped too, and exceptions and private networks
always get in. Only the ports the server serves (protocols, WireGuard, forwards) are filtered, so
SSH and the agent's own connection to the panel never are. Refused packets are counted per server.

The **site rule** is checked by the panel itself on every request, by area: the panel and its API,
the users' pages, the status page and (optionally) subscription links. The panel refuses to save a
rule that would refuse the person saving it.

## Reports and exact accounting

Every few seconds (Settings › report interval) the agent sends a report: live data (system load,
who is online, core status) plus a **batch** of accumulated counters - traffic per user, server
and protocol, connecting IPs, destinations, forward bytes, refused packets.

Batches carry the agent's instance id and a sequence number. The panel applies a batch only if its
sequence is newer than the last one it applied for that server, and acknowledges it; the agent keeps
unacknowledged batches in an on-disk outbox and resends them. A lost answer, a panel restart or an
agent restart therefore never loses or double-counts traffic.

Where the numbers come from:

| | Traffic | Online IPs | Destinations |
| --- | --- | --- | --- |
| Xray | stats API per user (`s<user>.n<node>`), read and reset | access log + online IP lists | access log (connections) |
| Hysteria2 | traffic-stats API, read and cleared | auth requests + `/online` | debug log (connections) |
| WireGuard | peer counters | peer endpoints | conntrack flows marked per interface (exact bytes) + a logging DNS resolver for names |
| Forwards | nftables counters per rule | - | - |

## Panel <-> agent channel

Each server has a 256-bit secret, shown only inside its install command. From it both sides derive
(HKDF-SHA256) a signing key and an AES-256-GCM key.

- **Requests** are signed: `HMAC-SHA256(method, path, unix time, random nonce, SHA-256(body))`. The
  panel rejects requests more than five minutes old and any nonce it has seen.
- **Bodies** in both directions are sealed with AES-256-GCM. Replies are bound to the request's path
  *and nonce*, so a recorded reply cannot be replayed to a later request.
- The **contract version** (`proto.Version`, now 4) is part of every state. An agent that is too old
  for its panel keeps running its last configuration, reports "the panel needs a newer agent" and
  accepts only an upgrade.

The channel is safe over plain HTTP; HTTPS is still recommended for the panel's web interface.

## Importing an existing setup

`scan` is an action like any other: the agent looks at running processes and the usual
configuration paths of Xray, V2Ray, x-ui, 3x-ui, sing-box and Hysteria2, reads their inbounds
(protocol, port, transport, security, keys, users) and reports them - it changes nothing. The panel
maps each inbound onto its protocol model (refusing, with a reason, anything it could not run
exactly), and an import creates protocols that keep the keys, and users matched by name or created,
with their own IDs and passwords. **Take over** sends a `stop_service` action for the old service
and enables the imported protocols on the same ports once it has stopped.

## Proxy pass

A protocol on an entry server can send its traffic out through a protocol on another server (the
exit). The panel gives the entry server an extra Xray outbound to the exit - authenticated with a
service credential derived from the entry server's secret - and a routing rule that sends the entry
protocol's traffic to it; the exit server simply gets one more user. Both are applied live. Chains
are one hop, which keeps behaviour predictable.

## Subscriptions

`/s/<token>` resolves the user's endpoints (every enabled protocol on the servers in their scope,
with their credentials) and renders the format the asking app needs - detected from the User-Agent
or forced with `?client=`. Usage, quota and expiry go into the standard `Subscription-Userinfo`
header. Browsers get a page with QR codes and import buttons. **Issue a new link** replaces only the
link token.

## The status page and the users' pages

Both are one static app (`web/status/index.html` and `web/src/status`), served by the panel for `/me`,
for `/status` or `/` when the status page is there, and for every path on the status page's own
domain. What it shows depends on who is signed in: visitors get the sign-in form; a user gets their
own page from `/api/portal/me`; the supervisor gets the dashboard from `/api/status` (every server,
cached for a few seconds, never containing users, addresses, ports or protocols) and
`/api/status/live` (the last 30 minutes of throughput). Availability is sampled every minute into
10-minute buckets per server (`server_uptime`) and reported for 24 hours, 30 days and per day.

## Data

One SQLite database in WAL mode, written through a single in-process writer queue. Main tables:
`accounts` (the supervisor), `sessions`, `api_tokens`, `servers`, `nodes` (protocols), `node_creds`
(imported credentials), `forwards`, `subs` (users) and `user_sessions`, `wg_peers`, `traffic_daily`,
`server_daily`, `forward_daily`, `ip_log`, `dest_log`, `server_metrics`, `server_uptime`,
`server_scans`, `events`, `actions`, `ip_blocks`, `settings`. Migrations run at start-up and are
append-only.
